# 결정 기록 (ADR)

eval 세트를 만들면서 정한 것과 그 이유를 남김. 라벨링 기준 자체는 `../rubric.md`, 필드 정의는 `schema.md` 에 있고, 이 문서는 **왜 그렇게 정했는가** 만 다룸. 기준을 바꾸려는 사람은 여기서 이유와 기각된 대안을 먼저 확인함.

- 형식: 번호, 상태, 배경, 결정, 대안과 기각 이유, 결과.
- 상태: `채택` 은 현재 적용 중, `폐기` 는 이후 결정으로 바뀐 것. 새 결정이 기존 결정을 바꾸면 기존 항목을 지우지 않고 상태를 `폐기(ADR-NNN 로 대체)` 로 바꾸고 새 항목을 추가함.
- 결정자는 gold 작성자 1명(사용자). 일자는 이 브랜치(`feature/eval_set`)의 커밋 이력에서 확인함.

## ADR-001. gold 검증과 잠금을 끝낸 뒤에 생성·채점

- **상태:** 채택
- **관련:** `../eval_overview.md` §1, `../README.md` §4

**배경.** gold 가 틀리면 judge 를 몇 번 돌려도 틀린 기준에 일관되게 맞출 뿐임. 라벨러가 1명이라 모델 출력을 본 뒤에 gold 를 맞추면 판단이 출력에 끌림(앵커링).

**결정.** 순서를 gold 작성(모델 출력을 안 봄) → 사람 검증(체크리스트 10건 + 블라인드 재라벨링 10건) → 잠금 → 생성 → 채점으로 고정함. 첫 baseline 은 사람이 gold 와 대조해 채점하고, 그 뒤에 judge(DeepSeek)를 도입함.

**대안과 기각 이유.** gold 검증 전에 생성이나 judge 를 돌리는 안은 틀린 gold 에 일관되게 맞추는 결과가 되어 기각.

**결과.** 잠금 전에는 생성도 judge 도 돌리지 않음. 잠금 뒤에 gold 를 고치면 세트 버전을 올리고 baseline 을 다시 돌려야 해서, 애매한 칸은 잠금 전에 정리함.

## ADR-002. `relative` 층 기준을 대형주 중간값으로

- **상태:** 채택
- **관련:** 커밋 `effc614`, `../rubric.md` §2, `../rubric.md` §2-1

**배경.** 초기 rubric 은 "코스피 대비 초과분"으로 `relative` 를 정의했음. 그런데 파이프라인이 실제로 쓰는 `market.excess_pct` 는 종목 등락 − **대형주 유니버스 중간값**(`peer_median_pct`, `stock_meta` 유니버스)임. 코스피 값은 보고서의 별도 비교 문장에만 쓰임.

**결정.** gold 의 `relative` 층 기준을 대형주 중간값 대비 초과분(`excess_vs_peers_pp`)으로 바꿈. 코스피 값(`kospi_*`)은 보고서의 코스피 비교 문장 검증용으로만 남김.

**대안과 기각 이유.** 코스피 기준을 유지하면 gold 의 `relative` 가 파이프라인이 계산하는 `excess_pct` 와 달라 채점기가 코드 값과 gold 를 비교할 수 없어 기각. 사용자가 rubric·gold 를 파이프라인 기준(대형주 중간값)에 맞추는 쪽으로 정함.

**결과.** 모든 케이스의 시장 칸과 판정을 다시 계산함. 일부 케이스는 코스피 기준과 판정 방향이 달라짐(예: 코스피와 비슷하게 움직였으나 대형주 대비로는 초과).

## ADR-003. 시장 칸은 코드 값을 옮김

- **상태:** 채택
- **관련:** `../rubric.md` §2-1, `add_case.md` §4

**배경.** `common_move`, `market_led`, `relative_direction`, `judge_layers`, `move_strength_cap` 은 파이프라인 코드(`verify.py`)가 규칙으로 계산하는 값임. 사람이 직접 쓰면 코드와 어긋날 수 있고, 어긋나면 축 D·E 채점이 틀림.

**결정.** 시장 칸은 같은 입력으로 `MarketCompare` 와 `verify` 함수를 돌려 나온 값을 옮기고 사람은 검수만 함. `relative_direction` 은 코드 출력값 그대로 한글(`더`/`덜`/`반대로`/`비슷하게`)로 둠.

**대안과 기각 이유.** 영어 라벨로 바꾸는 안을 검토했으나, 코드 출력값과 gold 를 대조하는 채점기가 번역 단계를 거치게 돼서 한글 출력값 유지로 결정.

**결과.** 시장 값은 라이브 KRX 와 현재 `stock_meta` 유니버스에 의존함. 평가 실행 전에 다시 계산해 gold 와 비교해야 함(`add_case.md` §7).

## ADR-004. 인과 강도를 3단계로, `direct_cause`·`definitive` 금지

- **상태:** 채택
- **관련:** 커밋 `6f03f80`, `../rubric.md` §4-2

**배경.** "모르는 것은 모른다고 처리"해서 할루시네이션을 잡는 것이 목적임. 처음 rubric 은 강도를 `coincident`/`possible_contributor`/`likely_cause`/`direct_cause` 4단계로 두고 단정 표현(`definitive`)도 다뤘음. 주가의 원인은 전문가도 확정하기 어려워서, gold 가 가장 센 단계를 허용하면 보고서의 과장을 gold 가 정당화하게 됨.

**결정.** `coincident`(같은 시기) / `possible_contributor`(영향 가능성) / `likely_cause`(주요 원인으로 지목) 세 단계만 둠. `direct_cause` 와 `definitive` 는 gold 에서 쓰지 않음. 헤지 없이 인과를 단정하는 문장은 보고서 쪽 값 `asserted` 로 보고 항상 상한 초과(`OVERCLAIM`)로 봄.

**대안과 기각 이유.** `direct_cause`(공시가 직접 원인)를 남기는 4단계 안은 가장 센 단정을 gold 가 허용하게 돼 기각. 사용자가 `definitive` 는 전면 금지, `direct_cause` 는 라벨링에서 삭제하기로 결정함.

**결과.** 기본 상한은 `likely_cause` 이고, 복수 원인인 날은 중요도별(`must`→`likely_cause`, `should`→`possible_contributor`, `optional`→`coincident`)로 낮춤. 방향이 반대인 재료, 풍문, 간접 재료, 장 마감 후 공개된 재료의 상한은 `coincident`.

## ADR-005. `confidence_level` 에서 `clear` 를 쓰지 않음

- **상태:** 채택
- **관련:** `../rubric.md` §3

**배경.** 확신 수준에 `clear` 를 두면 "원인이 확실한 날"이 존재한다고 gold 가 말하게 됨. 주가 원인은 확정하기 어렵다는 ADR-004 의 전제와 어긋남.

**결정.** 값을 `partial`(관련 재료가 있음) / `none`(입력에서 원인을 말할 근거가 없음) 두 개로만 둠. `none` 은 두 층 모두 `no_clear_cause`, `partial` 은 적어도 한 층이 `explained` 또는 `partially_explained` 일 때.

**대안과 기각 이유.** `clear`/`partial`/`none` 3단계는 원인이 명확한 날을 구분하지만 과신을 부추김.

**결과.** 원인이 명확한 날(예: c01)도 `partial` 로 표현됨. 원인이 명확한 날과 그렇지 않은 날은 `expected_verdict` 와 사건 중요도로 구분함.

## ADR-006. `must` 를 케이스당 0~2개로

- **상태:** 채택
- **관련:** `../rubric.md` §4-1

**배경.** `must` 는 빠지면 오답으로 치는 사건임. 처음에는 개수 제한이 없었고 사용자가 0~2개로 줄이기로 정함. 자세한 이유는 따로 기록하지 않았음(복수 원인인 날 `likely_cause` 를 받는 `must` 는 최대 2개라는 §4-2 규칙과 맞춤).

**결정.** `must` 는 케이스당 0~2개. 원인 없는 날(`none`)은 0개. 3개 이상이면 중요도를 다시 나눔.

**결과.** 10건 중 `must` 가 있는 케이스는 c01, c03, c09 세 건뿐임. 나머지는 `should`/`optional` 이라 축 C(누락) 판정이 느슨해짐. 이 한계는 알고 있으며, `must` 를 늘리려면 근거가 필요함.

## ADR-007. 판정값 경계 정의

- **상태:** 채택
- **관련:** 커밋 `e9a7656`, `../rubric.md` §2, 케이스별 `notes.md`

**배경.** 같은 재료도 라벨러에 따라 `explained` 와 `partially_explained` 가 갈렸음. 특히 같은 날 상충하는 요소(순이익 하회 등)가 있을 때와 직접 재료의 방향이 반대·혼재일 때가 문제였음.

**결정.**
- `explained`: 그 층을 직접 설명하는 재료가 있고 방향이 맞음. 같은 날 상충 요소가 있어도 낮추지 않고 상한과 `rationale` 로 다룸.
- `partially_explained`: 관련 재료는 있으나 간접·약함·일부. 방향이 맞아도 간접·미확인·약하면 여기에 둠.
- `no_clear_cause`: 그 종목의 직접 재료는 있으나 방향이 반대·혼재·불분명이거나, 재료가 없거나(유사 종목뿐), 재료가 급등락 이후에 나왔거나, 층의 크기가 ±1 이하이거나 `common_move` 인 날.

**대안과 기각 이유.** "상충 요소가 있으면 `explained` 를 낮춘다"는 조건은 처음 내가 덧붙였으나 루브릭에 없던 것이라 사용자가 빼고 `explained` 를 유지하기로 함(c01, c09 가 `explained`). 방향이 반대·혼재인 직접 재료를 `partially_explained` 로 두는 안은 사용자가 `no_clear_cause` 로 바꿈(c02, c05, c06, c08 판정이 바뀜).

**결과.** 10건 중 `confidence_level` 이 `none` 인 케이스가 6건(c02, c05~c08, c10)으로 쏠림. c06(교환사채 한 줄)과 c08(실적 혼재)은 대안으로 `partially_explained` 도 가능했으며, 어느 쪽이 맞는지는 리뷰에서 확인이 필요함. c04 의 `relative` 는 미확인 보도에 기대 `partially_explained` 임.

## ADR-008. 금지 주장은 구조화 조건 + 의미 대조

- **상태:** 채택
- **관련:** 커밋 `b9fbeba`, `../rubric.md` §5

**배경.** "외국인 매도가 하락 원인이다" 같은 문장을 gold 에 문자열로 적으면, 보고서가 "외국인 매도세 역시 약세에 영향을 미쳤습니다"라고 써도 못 잡음.

**결정.** 금지 주장을 `subject`/`relation_min`/`object`/`direction`/`type` 으로 구조화하고, 보고서 문장을 같은 구조로 뽑아 의미로 대조함. `example` 은 사람이 읽는 용도이며 대조에 쓰지 않음. 걸린 주장은 사람이 `quote` 로 확인함. `negated`(모른다고 쓴 문장)는 걸리지 않음.

**대안과 기각 이유.** 문자열 일치는 변형을 놓쳐 기각. 구조화 조건으로 적고 의미로 대조하는 방식으로 정했고, 의미 일치 판정을 judge 가 하더라도 걸린 주장은 사람이 확인함.

**결과.** 대조의 신뢰도는 judge 가 의미 일치를 얼마나 안정적으로 판단하는가에 달림. `relation` 척도는 `max_causal_strength` 와 같은 값을 쓰고 보고서 쪽에만 `asserted` 가 더 있음.

## ADR-009. `forbidden_claims` 는 hard fail 급만 적음

- **상태:** 채택
- **관련:** 커밋 `7824116`, `7026161`, 케이스별 `notes.md`

**배경.** 사건 상한(`max_causal_strength`)을 넘는 서술은 이미 `OVERCLAIM` 으로 잡힘. 금지 주장에 같은 서술을 중복해서 적으면 한 문장이 두 번 집계되고 케이스당 항목이 늘어 관리가 어려움.

**결정.**
- 입력으로 반증되는 hard fail 급만 적음: 유사 종목 인과, 방향 뒤집기, 입력에 없는 원인(외국인·기관 매매), 시장 비교 방향 오류.
- 케이스당 2~3개. 상한 초과는 events 의 `OVERCLAIM` 에 맡김.
- `advice`(매매 권유·목표가)는 케이스와 무관한 공통 hard fail(`HF_ADVICE`)이라 케이스별 gold 에는 넣지 않음.
- 미확인 보도를 사실로 확정해 쓰는 서술은 `unconfirmed_items` 와 `coincident` 상한으로 처리하고 금지 주장에는 넣지 않음.
- 원인 없는 날(`none`)의 원인 단정은 `relation_min: likely_cause` 로, 호재·악재 방향을 뒤집는 서술은 `possible_contributor` 로 둠.
- c10 의 "미 반도체 강세가 상승의 주된 요인"은 지나치게 엄격하다는 판단으로 뺌. c07 의 "삼성전자만 약했다"는 단순 비교 서술까지 막지 않도록 "삼성전자 고유 요인으로 하락했다" 는 원인 단정으로 좁힘.

**결과.** 외국인·기관 매매는 입력에 근거가 없는 `fabricated_cause` 로 9건에 넣었고(`relation_min: none`), 입력의 "수급"은 제품 수급, "기관"은 연구기관을 뜻해 투자자 매매와 무관함을 각 케이스 `notes.md` 에 적음.

## ADR-010. 출처는 증명 여부로 판정

- **상태:** 채택
- **관련:** 커밋 `814c5d6`, `../rubric.md` §4-3

**배경.** gold 에 허용 출처를 URL 목록으로 닫아 두면, 보고서가 같은 사실을 담은 다른 메시지를 인용해도 감점함. 반대로 출처 검증 없이 인용을 허용하면 환각을 못 잡음.

**결정.** 사건마다 `supporting_sources`(`{url, tier}`)와 `key_facts`(그 본문에 있어야 하는 사실)를 둠. 인용 판정은 URL 일치가 아니라 **그 source 본문이 사실을 증명하는지**로 함.
- URL 이 `supporting_sources` 에 있음 → 통과.
- URL 이 `case.json` 에 있고 본문에 `key_facts` 가 있음 → 통과(gold 에 없던 근거).
- URL 이 `case.json` 에 있으나 `key_facts` 가 없음 → `SOURCE_MISMATCH`.
- URL 이 `case.json` 에 없음 → `HF_FABRICATED` 후보.

`tier`(`primary`/`secondary`)는 기록용이고 감점 기준이 아님. gold 작성 시에는 `key_facts` 가 모든 `supporting_sources` 본문에 있어야 하고, 없으면 그 source 를 근거에서 뺌(검증 스크립트가 경고).

**대안과 기각 이유.** URL 완전 일치는 정상 인용을 감점함. `key_facts` 를 글자 그대로 일치로 대조하면 표기 차이(공백, 단위)에 취약해 `validate_gold.py` 는 공백·쉼표 무시, 금액 단위 환산, 낱말 부분 일치를 허용함.

## ADR-011. `published_at` 을 gold 에 쓰지 않음

- **상태:** 채택
- **관련:** 커밋 `f44a0ef`, `../rubric.md` §6

**배경.** 사건 공개 시각을 gold 에 따로 적으면 `case.json`·`provenance.json` 의 시각과 어긋날 수 있고, 수집기 DB 에 이미 같은 값이 있어 중복 입력이 됨.

**결정.** 사건의 공개 시각은 쓰지 않고 `supporting_sources` 의 시각(메시지는 `case.json` 의 `datetime_kst`, 공시는 `provenance.json` 의 `rcept_time_kst`)에서 계산함. 가장 이른 직접 근거가 기준이고, 장 마감(15:30) 이후 공개된 재료의 상한은 `coincident` 이하.

**결과.** 시각 판정이 근거 선택에 따라 달라지므로, 근거를 빼거나 바꾸면 사건의 시간 규칙도 다시 확인해야 함(검증 스크립트가 확인).

## ADR-012. `unknowns` 칸 추가

- **상태:** 채택
- **관련:** 커밋 `02c5ce5`, `../rubric.md` §5-1

**배경.** "모르는 것은 모른다고 처리"하도록 평가하려면, 입력에 **없는** 영역(수급, 덜/더 내린 이유 등)을 보고서가 단정했는지 볼 곳이 필요함. `events` 의 상한은 입력에 **있는** 사건을 얼마나 세게 말해도 되는지만 다룸.

**결정.** 케이스 전체에 붙는 `unknowns`(영역 목록)를 추가함. 보고서가 `unknowns` 영역을 단정하면 입력에 없는 사실은 `HF_FABRICATED`, 원인이면 `SPURIOUS_CAUSE`. "알 수 없습니다"는 감점하지 않음. `unconfirmed_items`(입력에 있으나 미확인)와 구분함.

**결과.** 모든 케이스에 "외국인·기관 수급"을 공통 항목으로 넣고, 케이스별로 입력으로 알 수 없는 영역을 추가함.

## ADR-013. 접수 시각을 확인하지 못한 공시는 근거로 쓰지 않음

- **상태:** 채택
- **관련:** 커밋 `4e2dafc`, `add_case.md` §3-4

**배경.** DART 공시 목록은 날짜(`rcept_dt`)만 주고 시각을 안 줌. 시각이 없으면 공시가 장중에 나왔는지 마감 후인지 알 수 없어 상한과 누수 판정을 할 수 없음.

**결정.** KIND 공시 목록으로 접수 시각을 확인하고(접수번호 일치 또는 9번째 자리 `8`↔`0`, 회사·제목 일치), 확인하지 못한 공시는 `rcept_time_kst: null` 로 두고 `case.json` 에도 gold 사건 근거에도 넣지 않음.

**결과.** 35건 중 30건의 시각을 채웠고 5건은 `null` 임(근거로 쓰지 않음). 공시 대신 같은 사실을 담은 텔레그램 메시지 URL 을 근거로 씀.

## ADR-014. 케이스 10건 모두 종목 단위로 유지

- **상태:** 채택

**배경.** 10건 중 2건을 코스피 전체 시장 케이스로 바꾸는 안을 검토함.

**결정.** 10건 전부 종목 단위로 둠. 코스피는 종목 케이스의 비교 문장(`kospi_*`)으로만 다룸.

**결과.** 시장 전체 설명 보고서의 품질은 이 세트로 보지 못함. 노리는 함정이 전부 종목 단위라, "잘 쓰는 날의 품질 저하"도 이 세트로는 못 봄(10건 모두 함정 케이스).

## ADR-015. 잠정 잠금을 기록하고 일부 칸을 해시에서 제외

- **상태:** 채택
- **관련:** 커밋 `620e0e8`, `../validate_gold.md` §9

**배경.** 정식 잠금 조건(체크리스트·블라인드 재라벨링 완료, `verification` 기록)이 아직 충족되지 않았음. `verification` 에 검증 완료를 쓰는 것은 사실이 아님.

**결정.** `lock_set.py` 로 `v0` 를 `provisional` 로 기록함(이후 팀원이 `cases_live/` 를 잠금 대상에 넣고 `v0.1`, `v0.2` 로 다시 기록함. ADR-019 참고). 해시 대상은 `case.json`, `provenance.json`, `gold.json`(`verification`·`status` 제외)이고, JSON 을 키 정렬로 정규화한 뒤 sha256 을 구함. 정식 잠금은 검증을 마친 뒤 `--provisional` 없이 기록함.

**대안과 기각 이유.** `verification` 을 임의로 채워 정식 잠금하는 안은 검증하지 않은 것을 검증했다고 적게 돼 기각. 잠금을 미루는 안은 잠금 전에 gold 가 소리 없이 바뀌는 것을 못 잡아 기각.

**결과.** 검증 기록을 채우거나 `status` 를 바꿔도 해시가 바뀌지 않음. gold 내용이 바뀌면 `--check` 가 알려 줌. 현재 기록은 `v0.2`(provisional, 13건)임.

## ADR-016. 평가 결과를 git 에 전부 커밋

- **상태:** 채택
- **관련:** `../README.md` §5

**배경.** 초기 계획(`eval_plan.md`)에는 `reports/` 를 git 제외로 적었으나 이유가 기록돼 있지 않았음. 개선 전후 비교에는 이전 판 결과가 필요하고, 사람이 채점한 baseline 은 다시 만들 수 없음.

**결정.** `ai/evals/reports/<eval_run_id>/` 의 모든 파일을 git 에 커밋함. `.gitignore` 에 넣지 않음.

**대안과 기각 이유.** 전체 제외는 baseline 이 지워지면 복구할 수 없어 기각. 요약(`summary.*`)만 커밋하는 안도 검토했으나 전부 커밋으로 정함.

**결과.** 결과 파일에는 텔레그램 원문 인용이 포함되므로, 외부 push 전에 데이터 사용 범위를 확인해야 함(`add_case.md` §9).

## ADR-017. `acceptable_alternatives` 는 쓰지 않음

- **상태:** 채택

**배경.** 칸 이름은 있으나 형식과 판정 규칙이 루브릭에 없음.

**결정.** 이번 세트에서는 채우지 않고 `[]` 로 둠. 재라벨링에서 어긋난 항목은 `rationale` 로 하나로 정하고, 정하기 어려우면 `verification.low_confidence` 에 적어 점수·개선 판정에서 제외함.

**결과.** 판정이 갈릴 수 있는 케이스(c04, c06, c08)의 대안 판정은 각 `notes.md` 에만 적혀 있고 채점에 쓰이지 않음. 칸을 쓰려면 형식과 판정 규칙을 먼저 `rubric.md` 에 정의해야 함.

## ADR-018. 규칙 A: 사건 강도에 따라 보고서 link 의 유무를 코드로 채점

- **상태:** 채택(팀 결정, 2026-11-10)
- **관련:** 커밋 `44ef420`, `20daf5e`, `8b60cf4`, `9875495`, `../score_rule_a.py`

**결정.** gold 사건의 `max_causal_strength` 가 `coincident` 이면 보고서에 그 사건 link 가 없어야, `likely_cause` 이면 있어야 정답으로 셈. `possible_contributor` 는 둘 다 정답이고 있음·없음을 따로 셈. 보고서 link 는 출처 URL 이 사건의 `supporting_sources` 에 있으면 그 사건, 없으면 입력 본문이 사건 `key_facts` 를 그대로 모두 담을 때 그 사건에 대응시킴. 어느 사건에도 안 맞으면 "gold 밖 link" 로 세어 사람이 확인함.

**세부(스크립트 주석에 적힌 내용).**
- `key_facts` 부분 일치(낱말 끝 한 글자를 뗀 대조)는 쓰지 않음. "IPO"·"SOX" 가 "IP"·"SO" 로 다른 메시지에 맞아 c03 에서 엉뚱한 사건이 잡혔음(2026-11-10).
- 그 케이스의 시황·오버나이트 메시지(c01·c07·c09)만 인용한 link 는 사건에 대응시키지 않고 "시황 메시지 link" 로 따로 셈.
- 대조 link(`direction_match=false`)도 위반 수에서 빼지 않음. 러너 판정이 `direction_match` 를 보지 않고 그 층 link 를 모두 세기 때문.

**결과.** 과장·출처 정확성 같은 의미 판단은 이 채점이 하지 않으므로 사람 채점은 남음. 실행 결과를 보고 gold 가 고쳐졌음: c02 e4 추가, c05 e2 분리와 e3 추가, c01·c03 `key_facts` 조정(각 `notes.md` 와 커밋 `6b5c463`, `9808e41` 참고).

## ADR-019. 실서비스 형식 입력 케이스(`cases_live`)를 안 A 와 분리해 잠금

- **상태:** 채택(팀원 작업)
- **관련:** 커밋 `a5bf2a3`, `d8b3136`, `b0f33f3`

**결정.** 기존 10건(`cases/`, 안 A 구형 입력)과 별도로 2026-11-05 실서비스 형식 입력 케이스를 둠. 채택한 b01·b04·b05 는 `cases_live/` 에서 `lock_set.py` 로 잠그고, 사람 검증 전인 b02·b03·b06 은 `cases_live_pending/` 에 두어 잠그지 않음. 잠금 키는 `cases_live/<폴더>` 로 하여 `cases/` 키를 그대로 유지함(예전 기록도 `--check` 로 비교 가능). b04 의 정정 공시 메시지에 `is_correction: true` 를 넣고 세트를 v0.2 로 올림.

**알려진 한계.** `cases_live/` 의 gold 는 claude-code 가 쓴 초안(`label_source: claude-code`)이라 사람 검증을 거치지 않았음. 안 B 를 채택한 이유와 b02·b03·b06 을 보류한 이유는 이 문서 작성자가 확인하지 못했음(해당 커밋과 팀원 기록 참고).
