# 종목 변동 보고서 Eval

종목이 왜 움직였는지 설명하는 보고서(`ai/` 파이프라인이 생성)를 **사람이 검증한 정답(gold)** 과 대조해 평가하는 10개의 eval set입니다.

- **목적:** 절대 점수가 아니라 프롬프트·모델을 고치기 전후를 같은 잣대로 비교하는 개선 추적입니다. 게이트는 모니터링이고 합격·불합격 기준으로 쓰지는 않고 있습니다.
- **범위:** 케이스 10건, gold 작성자 1명, 대상일 2026-10-19~10-30입니다. dev/test 분리는 없습니다.
- **한계:** 10건 모두 노리는 함정이 있어서 "원인이 명확한 날의 품질 저하"는 이 세트로 볼 수 없습니다. 비율 지표는 실서비스 성능을 대표하지 않고 "어떤 함정이 뚫렸나"를 보는 용도입니다.

## 1. 폴더 구조

```
ai/evals/
  README.md           이 문서
  eval_overview.md    평가 전체 요약(기준, 흐름, 채점 예시)
  rubric.md           gold 라벨링 기준(값 정의, 실패 유형)
  validate_gold.py    gold 검증 스크립트
  validate_gold.md    검증 스크립트 설명
  lock_set.py         세트 잠금 기록·변경 확인 스크립트
  gold.lock.json      잠금 기록(세트 버전, 상태, 케이스별 해시)
  docs/schema.md      데이터 스키마 레퍼런스
  docs/add_case.md    케이스 추가·수정 가이드
  docs/decisions.md   결정 기록(ADR)
  cases/<case_id>/    케이스 10건(안 A, 구형 입력)
  cases_live/<case_id>/          실서비스 형식 입력 케이스(안 B 중 채택한 b01·b04·b05, gold 는 claude-code 초안)
  cases_live_pending/<case_id>/  사람 검증 전 보류 케이스(b02·b03·b06). 잠그지 않음
```

케이스 폴더 하나에는 파일 4개가 있습니다.


| 파일                | 내용                                                   | 모델에 주는가             |
| ----------------- | ---------------------------------------------------- | ------------------- |
| `case.json`       | 모델 입력. `cutoff`(대상일 18:45 KST) 이전에 올라온 텔레그램 메시지      | 줍니다                 |
| `provenance.json` | 자료별 공개 시각 근거, 공시 접수 시각, 종목 별칭, 일부러 섞은 `cutoff` 이후 자료 | 주지 않습니다             |
| `gold.json`       | 사람이 쓴 정답지(판정, 사건, 금지 주장 등)                           | 주지 않습니다. 채점할 때만 씁니다 |
| `notes.md`        | 라벨링 중 망설인 점과 판단 이유                                   | 주지 않습니다             |

## 3. 어떻게 평가하는가

### 3-1. 기본 원리

모델은 `case.json` 만 보고 보고서를 씁니다. 채점할 때만 `gold.json` 을 꺼내 보고서와 대조합니다.

```
case.json ─→ [보고서 생성(케이스당 3회)] ─→ 보고서
                                              │ 대조
gold.json ────────────────────────────────────┤
                                              ▼
                축별 채점 → hard fail 확인 → 케이스 결과 → 수정 전후 비교
```

- 코드가 재는 것은 수치·방향어·시각·판정 일치처럼 틀릴 수 없는 규칙입니다. 과장·누락·출처·불확실성 같은 의미 판단은 사람이 합니다. 

- 나중에는 llm as a judge(DeepSeek)도 할 계획입니다

### 3-2. 평가 축 6개


| 축        | 보는 것                                     | 누가 재나                   |
| -------- | ---------------------------------------- | ----------------------- |
| A 출처 정확성 | 주장과 인용 출처가 맞는가                           | judge 초안 + 사람 확정        |
| B 인과 과장  | 문장 강도가 gold가 허용한 최대 강도 이하인가              | 강도는 judge·사람, 시간 선후는 코드 |
| C 원인 누락  | gold의 핵심 사건(`must`)을 담았나, 없는 원인을 만들진 않았나 | judge 초안 + 사람 확정        |
| D 시장 비교  | "더/덜 움직였다"가 KRX 수치·방향과 맞는가               | 코드                      |
| E 불확실성   | 원인 없는 날 지어내지 않았나, 판정·강도·서술이 맞나           | 코드 + judge              |
| F 초보자 이해 | 읽고 이해되는가                                 | 자동 지표 + 초보자 패널(3\~5건)   |


### 3-3. 인과 강도

gold는 사건마다 "말해도 되는 최대 강도"를 정해 둡니다. 보고서 문장이 이보다 세면 과장(`OVERCLAIM`)입니다.


| 값                      | 뜻              | 문장 예                |
| ---------------------- | -------------- | ------------------- |
| `coincident`           | 같은 시기에 발생했다    | "같은 날 \~도 있었습니다"    |
| `possible_contributor` | 영향을 줬을 가능성이 있다 | "\~영향을 줬을 수 있습니다"   |
| `likely_cause`         | 주요 원인으로 지목된다   | "\~가 주된 요인으로 풀이됩니다" |


### 3-4. 치명 실패(hard fail)

하나라도 있으면 그 보고서는 Reject입니다.


| 코드                | 뜻                           |
| ----------------- | --------------------------- |
| `HF_LEAKAGE`      | `cutoff` 이후 정보를 사용          |
| `HF_FABRICATED`   | 입력에 없는 사실·출처·수치             |
| `HF_CONTRADICTS`  | 인용 출처와 반대로 서술               |
| `HF_FALSE_CAUSE`  | 원인이 없는 날(또는 방향 불일치)에 원인을 단정 |
| `HF_MARKET_WRONG` | 시장 비교 방향(더↔덜)·수치 오류         |
| `HF_ADVICE`       | 매수·매도 권유, 목표가               |


일반 실패는 `OVERCLAIM`, `OMISSION`, `SPURIOUS_CAUSE`, `PLACEMENT`, `SOURCE_MISMATCH`, `UNCERTAINTY_MISSING`, `INCONSISTENT`, `BEGINNER` 입니다. 정의는 `rubric.md` §7 을 보시면 됩니다.

### 3-5. 채점 예시

보고서 문장이 "영업이익이 예상치를 크게 밑돌아 하락한 것입니다. 외국인 매도도 영향을 줬습니다."라고 가정합니다.


| 문장                 | 비교 기준                          | 결과                    |
| ------------------ | ------------------------------ | --------------------- |
| "영업이익이 … 하락한 것입니다" | 해당 사건의 허용 상한이 `likely_cause`   | 단정이라 `OVERCLAIM`(축 B) |
| "외국인 매도도 영향을 줬습니다" | `forbidden_claims` 의 입력에 없는 원인 | `HF_FABRICATED` 후보    |


`HF_*` 후보는 사람이 직접 확인해서 확정합니다.

## 4. 평가 절차

### A. 세트 만들기

평가셋은 현재 폴더의 cases 사용하면 됩니다

1. `case.json` 조립과 공시 접수 시각 확인
2. gold 작성(모델 출력을 보지 않고 `case.json` 만 보고 작성)
3. 검증: 체크리스트 10건(시각·출처·시장·판정·금지 주장)과 블라인드 재라벨링 10건
4. gold 잠금: `verification` 을 기록하고 `lock_set.py` 로 세트 버전·해시를 `gold.lock.json` 에 남깁니다. 잠금 뒤에 gold를 고치면 세트 버전을 올리고 baseline을 다시 돌립니다. 방법은 6장을 보시면 됩니다.

### B. 평가 실행(프롬프트·모델이 바뀔 때마다)

1. 케이스 10건을 생성합니다. 마감 이후 케이스는 KRX로 시장 비교를 계산하므로 `ai/.env` 의 KRX 키가 동작해야 축 D가 채점됩니다.
2. `verify_status` 가 `passed` 가 아니면 Reject로 셉니다. 코드가 판정 일치, 시각, 시장 비교 수치·방향어를 대조합니다.
3. 첫 baseline은 사람이 gold와 대조해 의미 판단(과장·누락·출처·불확실성)을 채점합니다.
4. 그 뒤 judge(DeepSeek)를 같은 생성 결과에 3회 돌려 초안을 내고, 사람 채점과 비교해 얼마나 믿을지 봅니다. 갈린 쌍과 hard fail 후보는 사람이 확인합니다.

### C. 개선 반복

1. 실패 유형을 분류하고 큰 문제 1~2개만 한 번에 하나씩 고칩니다.
2. 같은 세트로 재실행해 케이스별로 개선 / 동일 / 악화를 비교합니다.
3. 같은 프롬프트를 두 번 돌렸을 때의 흔들림(노이즈)보다 변화가 클 때만 개선으로 인정합니다.

## 5. 평가 결과 확인

결과는 파일로만 남기고 DB에는 적재하지 않습니다. 실행마다 `ai/evals/reports/<eval_run_id>/` 에서 확인하면 됩니다.

```
reports/<eval_run_id>/
  summary.md            사람이 읽는 요약
  summary.json          실행 단위 집계(기계용)
  cases/<case_id>.json  케이스 단위 채점 상세
  human_queue.jsonl     사람이 확인할 항목(hard fail 후보, judge 불안정)
```

### 어디를 보면 되는가


| 알고 싶은 것                        | 볼 곳                                                                                   |
| ------------------------------ | ------------------------------------------------------------------------------------- |
| 이번 실행의 한 줄 결론, hard fail 전체 목록 | `summary.md` 앞부분. hard fail 은 생략 없이 전부 나열합니다                                          |
| 축별로 어디가 약한지                    | `summary.md` 의 축별 요약, 태그별 약점                                                          |
| 지난번보다 나아졌는지                    | `summary.md` 의 이전 판 대비. 케이스별 개선 / 동일 / 악화로 보여 줍니다                                     |
| 한 케이스가 왜 그 점수인지                | `cases/<case_id>.json`. 축별 점수, 판정마다 근거 인용, 판정 주체(`code`/`judge`/`human`)가 있습니다        |
| 사람이 아직 확인할 것                   | `human_queue.jsonl`, `summary.md` 의 사람 검수 대기. 미확정 라벨은 "잠정"으로 표시됩니다                    |
| 실행 조건(재현용)                     | `summary.json` 의 meta. 프롬프트 해시, 생성 모델, judge 설정, 케이스 세트 버전, 시장 데이터 상태별 케이스 수가 들어 있습니다 |


`summary.md` 는 `summary.json` 에서 자동 생성하고 새로운 판단을 더하지 않습니다. 시장 데이터를 받지 못한 케이스(`no_data`, 실패)는 축 D를 N/A로 분리해 분모에서 뺍니다. 전후 실행에서 시장 데이터 상태가 다른 케이스는 비교에서 제외합니다.

## 6. gold 검증과 잠금 스크립트

`ai/` 폴더에서 실행합니다. 두 스크립트 모두 외부 패키지 없이 `python3` 만 있으면 됩니다.

### 6-1. 검증

```bash
python3 evals/validate_gold.py            # 10건 전체
python3 evals/validate_gold.py c07 c10    # 일부 케이스만
python3 evals/validate_gold.py --strict   # 아직 안 채운 칸도 오류로 처리
```

오류가 0건이어야 합니다. 무엇을 어떻게 검사하는지는 `validate_gold.md` 를 보시면 됩니다.

### 6-2. 잠금

잠금은 파일 권한을 막는 것이 아니라, 잠금 시점의 입력과 gold의 해시(파일 내용의 지문)를 `gold.lock.json` 에 기록해 두고 이후 바뀌었는지 확인하는 방식입니다.

```bash
python3 evals/lock_set.py --check                                  # 기록과 현재 파일 비교
python3 evals/lock_set.py --write --version v0 --provisional       # 잠정 잠금 기록
python3 evals/lock_set.py --write --version v1                     # 정식 잠금 기록
```

| 항목 | 내용 |
|---|---|
| 해시 대상 | `cases/` 와 `cases_live/` 의 케이스마다 `case.json`, `provenance.json`, `gold.json`. 기록 키는 `cases/` 케이스는 폴더 이름, `cases_live/` 케이스는 `cases_live/<폴더>` 입니다. `cases_live_pending/` 은 잠그지 않습니다 |
| 해시에서 빼는 칸 | `gold.json` 의 `verification`, `status`. 검증 기록을 채울 때 잠금이 깨지지 않게 하기 위함입니다 |
| `provisional` | 잠정 잠금. 체크리스트·블라인드 재라벨링·`verification` 이 끝나기 전 상태입니다 |
| `locked` | 정식 잠금. 위 검증을 모두 마친 뒤 `--provisional` 없이 기록합니다 |
| `--check` 결과 | 바뀐 케이스와 파일을 알려 주고, 변경이 있으면 종료 코드 1을 냅니다 |

잠금 뒤에 gold를 고치면 세트 버전을 올리고 `--write` 로 다시 기록한 다음 baseline을 다시 돌립니다. 현재 상태는 `gold.lock.json` 의 `lock_status` 로 확인합니다.

## 7. 지켜야 할 규칙

- gold는 `case.json` 만 보고 씁니다. 모델 보고서는 보지 않습니다(앵커링 방어).
- 입력에서 근거를 댈 수 있는 것만 씁니다. 그날 실제 원인을 안다고 해서 쓰지 않습니다.
- 원인을 하나로 단정하지 않습니다. 사건마다 중요도와 말해도 되는 최대 강도를 따로 적습니다.
- gold를 잠근 뒤에 고치면 세트 버전을 올리고 baseline을 다시 돌립니다.
