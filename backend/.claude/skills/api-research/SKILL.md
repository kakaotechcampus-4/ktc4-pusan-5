# API 심층 조사 스킬

시세/거시지표 등 외부 API를 서비스에 연동하기 전에, **실제 호출로 스펙을 검증**하고 문서로 남기는 절차. KRX·FRED 조사(`docs/api-research/krx.md`, `docs/api-research/fred.md`)에서 쓴 방법론을 표준화한 것.

## 핵심 원칙

- **문서보다 실호출을 믿는다.** 공식 문서가 로그인 후에만 보이거나 불명확하면 커뮤니티 자료로 초안을 잡되, 최종 결론은 반드시 실제 호출 결과로 검증한다. 문서와 실측이 다르면(예: FRED 문서는 분당 120건 제한인데 실측으로 150건 연속 성공) 둘 다 적되 실측을 우선 신뢰 표시로 남긴다.
- **아직 확인 안 된 건 "아직 못 알아낸 것"으로 솔직히 남긴다.** 추측으로 채우지 않는다.
- **이건 조사이지 구현이 아니다.** `app/services/`에 프로덕션 클라이언트를 만드는 단계가 아니다. 테스트 스크립트는 표준 라이브러리(`urllib` 등) 위주로 짧게, 일회성으로 짠다 — FastAPI 구조나 Pydantic 스키마를 여기서 미리 갖출 필요 없다.
- **비밀키는 절대 노출하지 않는다.** 저장하는 raw JSON, 문서, 커밋 메시지, 대화 응답 어디에도 실제 키 값을 그대로 남기지 않는다(`***REDACTED***` 처리).
- **커밋은 요청받았을 때만.** 조사 결과물(문서·스크립트·raw JSON)을 만드는 것과 git commit은 별개 — 커밋 여부는 항상 사람에게 확인한다.

## 준비

1. `.env`에 해당 API 키가 이미 들어있는지 확인한다(`grep -c "XXX_API_KEY=." .env`처럼 값 존재 여부만 확인하고 값 자체는 출력하지 않는다). 없으면 발급 방법을 안내하고 사람이 넣어줄 때까지 기다린다 — 대신 발급받으려 하지 않는다.
2. `.env.example`에 해당 키의 자리가 없으면 추가한다(값은 비워둠).
3. 폴더 구조를 만든다(없으면):
   ```
   docs/api-research/
     <api-name>.md              # 최종 스펙 문서
     raw/<api-name>/*.json       # 요청/응답 원문
     scripts/test_<api-name>.py            # 1차: 엔드포인트 존재 확인
     scripts/test_<api-name>_detailed.py   # 2차: 인증/요청/응답/데이터/운영 심층 검증
   ```

## 조사 절차

### 1. 겹치는 후보가 있는지 먼저 확인

같은 개념(예: "나스닥", "달러인덱스")에 대해 API에 여러 시리즈/엔드포인트가 있으면, 조사 중간에 웹서치나 메타데이터 조회로 후보를 찾아 **비교표를 만들고, `AskUserQuestion`으로 사용자 확인을 받은 뒤에** 최종 문서를 확정한다. 임의로 하나를 골라 진행하지 않는다.

### 2. 다섯 축을 전부 실호출로 검증

각 항목은 "문서에 뭐라고 되어있나"가 아니라 "실제로 호출해보니 어떻더라"로 채운다.

**[인증]**
- 토큰/키 발급 방식(OAuth vs 정적 키), 유효기간, 갱신 절차
- 키 발급 자체에 호출 제한이 있는지(대개 콘솔에서 하는 1회성 액션이라 해당 없음)
- 인증 실패를 실제로 유발해서 에러 형태 확인: 잘못된 키, 키 자체 누락을 각각 테스트 — 메시지가 다르면(예: KRX의 "Unauthorized Key" vs "Unauthorized API Call") 그 차이를 기록

**[요청]**
- 필수 헤더가 실제로 없으면 어떻게 되는지(에러 vs 조용히 이상 동작) 실제로 빼고 호출해서 확인
- 조회 단위가 단건인지 배치인지 — 여러 개를 한 번에 넣어보고(콤마 구분 등) 실제로 되는지, 조용히 무시되는지, 에러 나는지 확인
- 기간 조회 최대 건수, 페이지네이션 — `limit`/`offset`류 파라미터로 경계값 테스트(예: offset=0,limit=5 다음 offset=5,limit=5가 정확히 이어지는지)
- 문서에 없는 파라미터를 추가로 넣어봤을 때(예: 날짜 범위 파라미터) 무시되는지 에러가 나는지 확인 — API가 실제로 지원하는 기능의 경계를 파악하는 데 유용

**[응답]**
- 필드명·타입·단위를 실제 응답값으로 확인. **단위는 설명 문구만 믿지 말고 산술로 검증한다**(예: KRX `MKTCAP = LIST_SHRS × TDD_CLSPRC` 정확히 일치하는지 계산해서 원 단위·주 단위임을 증명)
- 등락률처럼 부호가 중요한 필드는 상승/하락 각각의 실제 값을 확인해서 표기 규칙을 적음
- 성공/실패를 구분하는 필드가 뭔지, 에러코드가 뭐가 있는지 실제로 여러 에러를 유발해서 확인
- **"데이터가 없음"과 "요청이 잘못됨"을 구분할 수 있는지 반드시 확인한다.** 파라미터 누락, 형식 오류, 존재하지 않는 값을 각각 보내보고, 정상적으로 데이터가 없는 경우(주말 등)와 응답이 같은 모양으로 오는지 다른 모양으로 오는지 비교한다. 같은 모양으로 온다면(KRX처럼) 그 사실 자체가 중요한 발견이니 문서에 명시하고 컬렉터 설계 시 주의사항으로 남긴다

**[데이터]**
- 지연/갱신 시각: 오늘 날짜로 조회했을 때 데이터가 있는지 확인해서 최소 지연을 실측한다. **지연일을 고정값으로 문서에 박지 말고, 조사 시점의 실측값이라는 걸 명시**한다(다음에 다시 조사하면 다를 수 있음)
- 휴장일 응답 형태: **반드시 과거에 실제로 있었던 확정 휴장일로 테스트한다.** 미래 날짜(아직 일어나지 않은 날)를 휴장일 테스트에 쓰면 "그냥 데이터가 아직 없어서" 빈 응답이 오는 것과 "휴장이라서" 빈 응답이 오는 걸 구분 못 해 무의미한 결과가 된다 — 테스트 전에 날짜의 실제 요일과 공휴일 여부를 `python -c "import datetime; ..."`나 웹서치로 미리 확인할 것. 휴장일 전후 영업일과 비교해서 패턴을 확인한다(예: 영업일-휴장일-영업일 3일 연속 조회)
- 수정값 반영 여부(주가 조정, 개정치 등), 코드 체계(지수 코드, 분류 코드 등)가 있는지 — 없으면 "해당 없음, 이유: ..."로 명시

**[운영]**
- 점검 시간대: 공식 문서/포털 공지에서 검색. 못 찾으면 "확인 불가"로 남긴다
- 요청 제한: 문서상 수치를 확인하고, **실제로 연속 호출을 여러 차례 해서 실측한다.** 단, 일/월 단위 총량 제한이 있는 API(예: KRX 일 10,000건)는 그 한도를 소진하는 방식으로 테스트하지 않는다 — 짧은 버스트(수십 회 수준)로 "이 페이스에서는 문제없다"는 정도만 확인

### 3. 모든 요청/응답 원문을 저장

- 실제로 호출한 요청(URL, 파라미터, 헤더 — 키는 redact)과 응답 전체를 `docs/api-research/raw/<api-name>/`에 JSON으로 저장한다. 파일명은 검증 항목을 알 수 있게 짓는다(예: `01_series_meta_VIXCLS.json`, `02_error_invalid_api_key.json`, `04_holiday_window_DGS10.json`)
- 여러 엔드포인트/시리즈를 순회하는 스크립트를 짜서 한 번에 저장하는 게 효율적 — `test_<api-name>_detailed.py`에 `save_raw()` 헬퍼로 일괄 처리

### 4. 최종 문서 작성 — `docs/api-research/<api-name>.md`

아래 구조를 따른다(KRX·FRED 문서가 실례):

1. 조사일, 대상, 참조할 스크립트/raw 경로
2. (있으면) 겹치는 후보와 확정 근거
3. 개요 표(포털, Base URL, 인증 방식 등)
4. [인증] / [요청] / [응답] / [데이터] / [운영] — 항목별 표, 실측 근거와 raw 파일 경로를 같이 적음
5. 엔드포인트/시리즈별 상세 스펙 — 요청 예시, 응답 원문(그대로 붙여넣기), 필드 매핑 표(필드명·타입·단위·설명), 특이사항
6. 기능별 매핑(요청받은 기능 → 실제 사용할 API/시리즈)
7. DB 스키마 매핑 시 주의사항 — 이번 조사에서 발견한 함정(단위, asOf 계산 방법, 결측 처리, 코드 체계 불일치 등)
8. 아직 못 알아낸 것 — 실호출로 확인 못 한 항목을 솔직하게 나열

### 5. 마무리

- 새로 짠 스크립트는 `uv run ruff check docs/api-research/scripts/`로 린트한다
- `git status`로 뭐가 바뀌었는지 확인하되, **커밋은 사용자가 명시적으로 요청할 때만** 한다
- raw JSON에 키가 그대로 남아있지 않은지 최종적으로 한 번 grep해서 확인한다

## 참고 사례

- `docs/api-research/fred.md` — 겹치는 시리즈(나스닥 종합 vs 나스닥100, 달러인덱스 여러 종) 확인 후 사용자 컨펌 받은 사례, `units=pch`로 등락률 계산 시 결측 연쇄 문제 발견
- `docs/api-research/krx.md` — "데이터 없음"과 "에러"가 구분 안 되는 API의 사례, 휴장일 테스트를 미래 날짜로 잘못했다가 과거 확정 휴장일로 교정한 사례, `MKTCAP = LIST_SHRS × 종가` 산술 검증 사례
