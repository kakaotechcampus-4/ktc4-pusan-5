# 같은 사건 묶기 설계

상태: 1단계 구현 완료(11절 1~5). 8절 시험과 합격 기준은 남았고 2단계는 정하지 않았다. 배경과 측정 결과는 [CLASSIFICATION_TUNING](CLASSIFICATION_TUNING.md) 2-6 이다.

## 1. 목적

같은 사건을 다룬 자료를 묶고, 몇 개 자료가 다뤘는지 센다. 뉴스·PDF·메시지를 함께 본다.

글자 겹침으로는 부족하다. 매체마다 문장을 다시 써서 요코하마 기사 28건을 묶어도 27묶음이 남는다. 대표 기사만 분류하지도 않는다. 같은 이야기여도 기사마다 담긴 사건이 다르다.

## 2. 범위

| | 1단계 (이 브랜치) | 2단계 (별도 결정) |
| --- | --- | --- |
| 하는 일 | 분류가 끝난 사건을 묶고 개수를 함께 낸다 | 같은 사건이면 판정을 재사용한다 |
| 비용 | 묶기 호출만큼 늘어난다 | 판정 비용이 줄어든다 |
| 기존 분류 흐름 | 바꾸지 않는다 | 추출·연결과 판정을 나눈다 |
| 먼저 끝날 일 | 없음 | 동시 처리, 판정 정확도 |

## 3. 정한 것

- 묶기와 개수 세기는 같이 낸다. 묶기만 먼저 합치지 않는다.
- 모델은 분류의 다른 단계와 같은 방식으로 정한다(`CLASSIFICATION_SAME_EVENT_MODEL`, 없으면 `SUMMARY_MODEL`). 지금까지 시험한 모델은 `openai/gpt-6-luna` 다. Elice 는 모델마다 주소·단가가 다르므로 모델을 바꿀 때 `LLM_BASE_URL`·단가도 같이 바꾼다. 쓴 모델은 호출 기록에 남긴다.
- 대상은 현재 회차(`is_current`)의 `company`·`industry` 사건이다. 실험 회차는 뺀다.
- `macro`·`market` 사건은 처음에는 묶지 않는다. 표기가 넓어 잘못 묶이기 쉽고 판정도 하지 않는다.
- 공개 시각(`available_at`)이 없는 자료는 처음에는 묶지 않는다. 시간으로 후보를 좁힐 수 없다.

## 4. 흐름

```text
아직 묶지 않은 대상 사건을 자료별로 모은다 (공개 시각이 빠른 자료부터, 한 자료씩)
  → 사건마다 후보 묶음을 찾는다
  → 자료 하나에 LLM 을 한 번 부른다
  → 사건마다 기존 묶음에 넣거나 새 묶음을 만든다
```

분류를 마친 뒤 별도 명령으로 돌린다.

**같은 사건의 정의.** 주체가 같고, 그 주체의 같은 일(행위·발표·수치·전망)을 말한다. 표현은 달라도 된다. 주제나 회사만 같으면 다른 사건이다. 판단이 어려우면 묶지 않는다.

**후보 조건.** 코드가 먼저 좁히고, 아래를 모두 만족하는 묶음만 LLM 에 보낸다.

- 묶음 대표 사건과 scope 가 같다.
- 연결 코드(종목·산업·외부 기업)나, 연결되지 않은 표기(`normalize_mention` 기준)가 하나 이상 겹친다.
- 묶음 대표와 공개 시각 차이가 48시간 안이다.

**대표하고만 견준다.** 대표는 묶음을 처음 만든 사건이고 바뀌지 않는다. 구성원끼리 이어 붙이면 A~B, B~C 가 비슷할 때 다른 사건인 A 와 C 까지 합쳐진다.

**LLM 입력과 출력.** 입력은 새 자료의 사건 문장(문맥 포함)과 후보 묶음의 대표 문장이다. 본문 전체는 보내지 않는다. 후보가 없는 사건만 있는 자료는 부르지 않고 새 묶음을 만든다.

```json
{"assignments": [{"event": 1, "cluster": 42}, {"event": 2, "cluster": null}]}
```

**응답 검사.**

| 경우 | 처리 |
| --- | --- |
| 후보 밖 묶음 번호 | 새 묶음으로 처리하고 건수를 남긴다 |
| 응답에 없는 사건 | 묶지 않은 채로 둔다. 다음 실행에서 다시 본다 |
| 호출 실패·JSON 깨짐 | 그 자료는 묶지 않은 채로 둔다. 응답 원문과 오류를 남긴다 |

호출이 실패해도 분류 결과는 바뀌지 않는다.

**재분류.** 새 회차의 사건은 아직 묶이지 않은 사건으로 다시 처리한다. 이전 회차 사건의 소속은 지우지 않고 조회에서 현재 회차만 본다.

## 5. 저장

기존 분류 표는 바꾸지 않고 표 3개를 더한다(마이그레이션 `0029`).

| 표 | 칸 | 설명 |
| --- | --- | --- |
| `classification_event_clusters` | `id`, `representative_event_id`, `created_at` | 묶음 하나 |
| `classification_event_cluster_members` | `event_id`(PK), `cluster_id`, `call_id` | 사건의 소속. 사건 하나는 묶음 하나에만 든다 |
| `classification_cluster_calls` | `id`, `source_card_id`, `status`, `model`, `prompt_sha256`, `raw_response`, `error`, `usage`, `fixes`, `created_at` | LLM 호출 기록. 후보가 없어 부르지 않으면 행을 만들지 않는다 |

프롬프트는 `app/llm/prompts/classification_same_event.md` 에 둔다.

## 6. 개수

개수는 저장하지 않고 조회할 때 센다. 기준 시각 뒤에 나온 자료가 수에 들어가면 안 되기 때문이다.

- 현재 회차 사건만 센다.
- `available_within(until, since)` 와 `body_observed_by(record, observed_by or until)` 를 통과한 자료만 센다. `classified_sources` 와 같은 규칙이다. 보고서 입력(`--target-date`)은 공개 끝(`until`)을 대상일 장 마감으로, 본문 끝(`observed_by`)을 실제 기준 시각으로 나눠 주므로, 장 마감 뒤에 본문을 받은 자료도 목록과 수에 똑같이 들어간다. `observed_by` 를 안 주면 `until` 이다.
- `source_count` 는 서로 다른 자료 수다. 한 자료의 사건 둘이 같은 묶음이어도 1이다.
- `publisher_count` 는 서로 다른 출처 수다. 한 매체가 고쳐 올린 기사는 `source_count` 만 늘린다.
- `counts_by_type` 은 자료 종류별 수다. 예: `{"news": 3, "pdf": 1, "message": 1}`
- 같은 묶음에서 세는 자료를 링크로 공유한 메시지는 세지 않는다. 기사 하나가 두 건으로 보이면 안 된다. 링크 대상이 기준 시각에 세어지지 않으면 메시지를 센다. 메시지에 자기 해설이 있어도 뺀다는 대가가 있다.

`classified_sources` 의 사건마다 `cluster_id` 와 위 값을 더한다. 묶이지 않은 사건은 `cluster_id` 가 없고 개수도 없다. 생성 쪽에서 이 값을 어떻게 쓸지는 생성 담당과 정한다.

## 7. 명령

```powershell
# 저장한다
uv run python -m app.services.classification same-event --since 2026-11-01 --limit 200

# 저장하지 않고 결과와 비용만 본다
uv run python -m app.services.classification same-event --since 2026-11-01 --limit 200 --dry-run
```

출력은 묶음별 `source_count`·`publisher_count`·`counts_by_type`, 호출 수, 실패 수, 비용이다.

한 번에 하나만 돈다. 나중 실행은 앞 실행이 끝날 때까지 기다렸다가 그때 남은 자료를 고른다. `--dry-run` 도 마찬가지다. 겹치면 같은 자료에 비용을 또 쓰고, 뒤에 저장하는 쪽이 오류로 멈춘다. 분류 `run` 과는 겹쳐도 된다. 도중에 생긴 새 회차는 다음 실행이 묶는다.

## 8. 시험

판정 정확도 작업(`feature/classification-accuracy`)이 끝난 뒤 돌린다. 추출이 바뀌면 묶기도 다시 해야 한다. 한 번 더 분류하는 데 드는 돈을 아끼기 위한 순서다.

- 표본: 특정 하루의 뉴스 약 200건. 분류에 약 ₩500(건당 약 ₩2.3)이 들 것으로 본다. 묶기 비용은 재 봐야 한다.
- 다시 재는 이유: 이전 시험은 같은 표기의 사건 목록을 한 번에 묶었고, 이 설계는 자료마다 대표와 견준다. 방식이 달라 이전 결과를 그대로 쓰지 못한다.
- 사람이 묶음 표본을 읽고 잘못 묶음과 놓침을 잰다. 이전 시험의 정답은 AI 가 만들었고 사람이 검토하지 않았다.
- 볼 값: 잘못 묶음 비율, 놓친 비율, 자료당 묶기 비용, 후보가 가장 많이 몰린 호출의 크기, 재사용할 수 있는 판정 비율.

합격 기준은 아직 정하지 않았다. 표본 결과를 보기 전에 팀에서 정한다.

## 9. 2단계를 정할 때 볼 것

- 판정은 기사마다 본문 전체를 보낸다. 일부 사건을 건너뛰어도 본문 입력 비용은 남으므로 실제 토큰으로 절감액을 다시 계산한다.
- 재사용하려면 추출·연결을 모두 끝낸 뒤 묶고, 그다음 판정하도록 흐름을 나눠야 한다. 중간 결과 저장 방식도 정해야 한다.
- 나중에 공개된 사건의 판정을 먼저 공개된 사건에 쓰지 않는다. 지금 `run` 은 최근 자료부터 처리한다.
- 같은 묶음이어도 후보 경로가 다르면 판정을 재사용하지 않는다.
- 잘못 묶이면 틀린 판정이 그대로 복사된다. 1단계의 잘못 묶음 비율이 전제 조건이다.

## 10. 아직 모르는 것

- 삼성전자처럼 기사가 몰리는 종목에서 48시간 안의 후보 묶음이 몇 개까지 늘어나는가. 이전 시험에서는 사건 25개를 한 번에 보낸 호출이 ₩1.16 이었다. 상한이 필요한지는 시험에서 본다.
- 자료마다 대표와 견주는 방식이 사건 목록을 한 번에 묶는 방식만큼 찾아내는가.
- 공개 시각이 없는 자료와 `macro`·`market` 사건을 언제 넣을 것인가.
- 표기가 달라 후보에 오르지 못하는 사건이 얼마나 되는가. 소규모 시험에서 "삼성"으로만 적힌 사건이 "삼성전자" 묶음의 후보에 오르지 못했다. 조건을 넓히면 호출과 잘못 묶음이 함께 늘 수 있어 표본에서 빈도를 보고 정한다.

3. 프롬프트와 묶기 실행 (`llm.py` 에 단계 추가)
4. 저장과 `same-event` 명령
5. 개수 조회와 `classified_sources` 추가
6. 8절의 시험
