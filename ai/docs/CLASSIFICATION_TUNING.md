## 2. 과제

### 2-1. 지분 방향 오판

모회사 소식이 피보유사에 `INDIRECT_CONTEXT` 로 붙는다. 예: 삼성전자의 요코하마 연구거점 소식 → 삼성SDI·삼성바이오로직스. 판정 이유에 "삼성전자 지분을 보유" 처럼 방향을 거꾸로 적기도 했다. 기준 JSON 의 `company_relations` 에서는 삼성전자가 지분을 가진 쪽이다.

- 근거: 후보의 관계가 피보유(`owned`)뿐인 판정 55건 중 NOT_APPLICABLE 41건, INDIRECT_CONTEXT 14건(삼성SDI 7, 삼성바이오로직스 7. 자료 240·255·259). 판정 프롬프트는 지분 관계를 "자회사·투자회사의 소식 → 지분을 가진 회사의 배경" 으로만 적는다. 그 기준이면 14건은 오판이다.
- 영향: 피보유사 보고서에 모회사 소식이 잡음으로 들어간다.
- 방법 A: 지분을 가진 쪽에서 피보유사로 넓히지 않는다(`candidates.py`). 55건의 판정 자체가 사라져 비용도 준다. 5-1 의 "양방향" 설계를 바꾸므로 팀 결정이 필요하다. 공급 관계가 같이 있는 삼성전기(24건)는 그 관계로 후보에 남는다.
- 방법 B: 판정 프롬프트에 방향 규칙을 명시한다. 코드는 그대로지만 LLM 이 또 틀릴 수 있고 판정 비용도 그대로다.

### 2-2. 같은 사실에 다른 판정

요코하마 연구거점 기사 다섯 건에서 삼성생명 판정이 갈렸다. 자료 235·255·259 는 INDIRECT_CONTEXT, 236·247 은 NOT_APPLICABLE.

- 영향: 어느 기사가 먼저 잡히느냐로 보고서 입력이 달라진다.
- 방법: 판정 프롬프트의 지분 기준을 구체화한다. "회사의 실적·가치 소식" 에 연구 투자·경영 활동이 드는지 정한다. 2-6 중복 묶기로도 빈도가 준다.

### 2-3. 기준에 없는 회사의 기사를 놓친다

회사 사건은 산업 경로를 타지 않는다(5-1). 그래서 기준에 없는 회사의 기사는 산업 단어가 있어도 후보가 생기지 않는다.

- 자료 2681 (CXMT 6세대 D램): CXMT 사건에 삼성전자·SK하이닉스 후보 없음. 삼성전자는 같은 기사의 SK하이닉스 문장으로만 닿았다.
- 자료 339 (최태원·오픈AI HBM 협력): "SK" 는 막은 표기이고 오픈AI 는 미등록이라 후보가 하나도 없다.
- 방법: 새 기준 파일에 외부 기업과 관계를 더한다. 외부 기업은 관계가 있어야 하고 관계는 근거가 있어야 한다(RELATION_REVIEW 2절). 회사 사건에 산업 경로를 여는 것은 하지 않는다. 회사 소식 하나가 업종 전체로 퍼진다.
- "SK" 처럼 공식 이름이 막은 표기와 같은 경우의 처리는 따로 정한다. 기사 표기 "SK(034730)" 처럼 종목코드가 붙으면 확정할 수 있을지 본다.

### 2-4. 묶음 표기를 연결하지 못한다

자료 978 의 "현대차·기아" 가 표기 하나로 나와 그 사건에 현대차·기아 후보가 없다.

- 방법: 추출 프롬프트에서 회사별로 나눠 쓰게 하거나, 연결 전에 `·` 로 나눠 사전을 찾는다. 후자는 "카드·결제" 같은 산업 이름과 부딪히지 않게 사전을 먼저 본다.

### 2-5. 표기 연결 LLM 이 거의 항상 불린다

20건 중 19건에서 불렸고 비용의 19% 다. 사전에 넣으면 되는 표기와, 고를 코드가 없는 회사 이름이 함께 간다.

- 미연결 상위: APL 8, 한미반도체 7, CXMT 4, 오픈AI 4, TCL CSOT 3. LLM 이 고른 표기 예: 낸드플래시, PC용 D램, 낸드 가격.
- 방법: 자주 나오는 표기를 새 기준 파일에 별칭으로 넣는다(낸드플래시, APL → 삼성전자 등). 고를 코드가 없는 회사 이름을 LLM 에 보내지 않을 방법을 본다.

### 2-6. 같은 사건 기사를 건마다 분류한다

요코하마 방문 기사는 제목이 다른 것만 최소 8건이다. 제목이 완전히 같은 뉴스는 2,276건 중 45건뿐이라 제목 일치로는 못 묶는다.

- 먼저 할 일: LLM 없이 중복 비율을 잰다. `uv run python -m app.services.classification dedupe-measure` (DB 읽기만 한다). **아직 재지 않았다.**
- 방법: 대표 기사 하나만 LLM 에 보내고 나머지는 묶음으로 남긴다. "여러 매체가 보도했다" 는 정보가 사라지지 않게 묶인 수를 남긴다. 기사 수와 매체 수를 따로 센다. 한 매체가 고쳐 올린 기사는 기사 수만 늘린다.
- 잃는 것: 대표만 분류하므로 묶인 기사에만 나오는 내용은 빠진다. 측정표의 "대표에 없는 종목" 이 그 크기다(이름 일치 기준). 저장 방식과 기준값은 이 값과 검토표를 본 뒤 정한다.
- 조회 때 주의: 기준 시각 뒤에 나온 기사는 수에 넣지 않는다. 보고서에 그 시점에 없던 수가 들어가면 안 된다.

### 2-7. 순차 처리

`run` 이 자료를 한 건씩 처리한다(건당 약 22초). 본문 있는 자료 2,465건이면 약 15시간이다. 저장은 자료마다 세션이 따로이고 행을 잠그므로 동시 처리를 막는 구조는 아니다.

- 방법: `--concurrency` 를 더한다. `collectors/summary.py`·`collectors/stock_analysis.py` 의 Semaphore 방식을 따른다.
- 주의: 분류 호출은 재시도가 없어 429 가 나면 그 자료가 `failed` 로 저장된다. Elice 속도 제한을 모르니 3건부터 본다. 비용은 줄지 않는다.

### 2-8. 긴 자료

- 2만 자를 넘는 PDF 는 건너뛴다(본문 있는 PDF 257건 중 19건).
- 사건이 8개 나온 자료가 2건이다(929, 379). 8개는 프롬프트의 지시이고 코드는 자르지 않는다(파서는 9개도 받는다). 모델이 지시를 따르느라 뺀 사건이 있는지는 원문과 대조해야 안다. 시황 리포트처럼 여러 종목을 다루는 자료는 뒷부분이 빠질 수 있다.
- 줄바꿈마다 문장이 나뉘어 자료 929 는 410문장이다.
- 방법: 나눠 보내는 단위를 먼저 설계한다. CLASSIFICATION_DB_DRAFT 11절의 미정 항목과 같은 문제다.

### 2-9. 보고서 입력 상한 (생성 담당과 협의)

`classified_sources` 에는 개수 상한이 없고, macro·market 사건은 모든 종목에 붙는다. 표본 20건 중 4건에 그런 사건이 있었다. 전체 자료를 돌린 뒤 입력이 얼마나 커지는지 재고, 판정 라벨·시간 기준으로 몇 건까지 넘길지 생성 담당과 정한다.

### 2-10. PDF 본문을 다시 추출해야 할 때

설계는 "원문은 한 번 확보하면 바뀌지 않는다" 를 전제로 문장 번호를 근거로 쓴다. 첫 PR 에서 네이버 PDF 저장(`repositories/analyst_report.py`)도 정상 본문을 덮어쓰지 않게 했다. 그래서 지금은 추출기를 개선해도 저장 함수로 기존 본문을 바꿀 수 없다.

- 필요해지면: 본문 재추출을 별도 작업으로 만들고, 바뀐 자료의 회차를 무효화해 재분류 대상으로 넣는다. 본문 확보 시각도 그 작업이 함께 갱신한다.
- `input_sha256` 은 저장만 하고 비교하지 않는다. 재추출 작업을 만들 때 조회에서 해시 불일치를 검출할 방법을 함께 본다.

### 2-11. 사용량을 모르는 호출이 ₩0 으로 합산된다

`cost_detail` 은 사용량이 없으면 `(0.0, "unavailable")` 로 구분하지만, `ClassificationResult.cost` 와 CLI 합계는 숫자만 더한다. 표본 20건의 합계에는 해당 호출이 없어 영향이 없었다.

- 방법: 미확인 호출 수를 함께 세고 합계를 "확인된 비용" 으로 표시한다.

### 2-12. 관계가 없는 기준은 동기화에 실패한다

`sync_basis` 가 빈 목록에도 INSERT 를 실행해 `DEFAULT VALUES` 가 되고 NOT NULL 제약에 걸린다. 지금 기준 파일은 관계가 있어 일어나지 않는다.

- 방법: 빈 목록이면 INSERT 를 건너뛴다. 빈 기준을 금지할 생각이면 `parse_basis` 에서 거부한다.

### 2-13. 표기 연결 LLM 의 오연결

코드 선택 결과는 목록 안의 코드인지만 본다. LLM 이 "CXMT" 를 `005930` 으로 고르면 삼성전자가 `company`, `direct_allowed = true` 후보가 된다. 프롬프트가 막고 있지만 코드 방어는 없다.

- 먼저 할 일: 표본의 `linked_by = llm_code` 28건을 사람이 대조해 실제로 틀린 연결이 있는지 본다. **아직 대조하지 않았다.**
- 방법: 종목·외부 기업으로 이어진 `llm_code` 연결은 DIRECT 를 막거나, 표기가 그 회사 이름과 닮았는지 코드로 확인한다.

uv run python -m app.services.classification eval --articles <표본 articles.json>

## 5. 결정 기록

첫 PR 을 준비하며 정한 것과 이유다. 건수와 비중은 2026-11-02 DB 기준이고, 11월 1일 일괄 수집의 영향이 있을 수 있다.

### 5-1. LLM 이 본문을 여러 번 읽는 구조는 유지하고 비용을 본 뒤 정한다

분류 자료는 모두 사건 추출(①)과 판정(④, 후보가 있을 때)에서 전문을 읽는다. 텔레그램 PDF 는 수집 쪽 요약 배치(`collectors/summary.py`)에서도 전문을 읽는다. 네이버는 API 가 요약을 줘서 이 배치를 타지 않는다.

- 요약으로 분류를 대신하지 않는다. 분류 근거는 본문의 문장 번호이고, 요약에는 그 번호가 없다.
- ①과 ④를 합치지 않는다. 추출이 끝나야 후보를 정할 수 있고, 합치면 기준 데이터 전체를 매번 보내야 한다.
- 다음에 볼 것: 단계별 비용을 확인하고, 판정 입력을 제목과 근거·문맥 문장으로 줄여도 정확도가 유지되는지 비교한다. 모델 비교(3절)와 함께 한다.

### 5-2. 기준 JSON 은 파일 하나로 둔다

산업·종목·기업 관계가 서로 연결되어 있어 기능별로 나누지 않았다. 지금은 `2026-11-03-draft.json` 을 쓴다.

- 이유: 회차에 해시 하나로 기준 버전을 남기고, 섹션 간 참조를 `parse_basis` 에서 한 번에 검사한다. 나누면 파일 버전의 조합을 따로 기록해야 한다.
- 대가: 별칭 하나만 고쳐도 새 파일을 만들어야 하고, 동시에 고치면 충돌하거나 버전이 갈라질 수 있다.
- 다시 볼 때: 여러 명이 동시에 고치거나 산업이 크게 늘면 편집용 파일만 나누고, 합친 파일로 지금처럼 검사한다.

### 5-3. 텔레그램 채널을 7개로 늘린다

처리량이 걱정되어 처음에는 보류를 검토했지만, 쏠림을 줄이려면 필요하다고 판단을 바꿨다.

- 근거: 30종목 중 23종목은 텔레그램 메시지와 링크 기사에 이름이 나오지 않는다. 이름 일치로 센 값이라 산업 이야기는 빠져 있다.
- 처리량: 텔레그램은 전체 건수의 3%(74건)라 늘려도 영향이 작을 가능성이 높다. 실제 증가 폭은 추가한 뒤 잰다.
- 기준: 채널 수보다 어떤 분야를 채우느냐를 본다. 후보는 금융, 자동차, 조선·방산, 2차전지, 시황이다.
- 작업은 분류기와 별도의 채널 브랜치에서 한다. 3절의 브랜치 구성에는 넣지 않는다.

### 5-4. 수집량보다 LLM 에 넣는 양을 먼저 줄인다

수집하지 않은 기사는 나중에 다시 쓸 수 없다. 원문은 저장해 두고 분류 입력을 줄인다.

- 분량: 네이버 뉴스가 건수의 87%, 글자 수의 49%다. 네이버 리서치 PDF 는 건수의 10%, 글자 수의 45%다.
- 제목 필터는 쓰지 않는다. 삼성전자가 언급된 기사 533건 중 제목에도 있는 기사는 78건이라, 산업 기사와 언급 기사 대부분이 빠진다.
- 먼저 할 방법은 중복 묶기(2-6)다. `--display` 축소는 최신순이라 앞선 시간대 기사가 먼저 빠져 뒤로 둔다.
